## 3. Наблюдаемый формат против предполагаемой семантики

**EVIDENCE — только указанные окна S014/S015:**

- В обоих образцах видны три поля, разделённые пробелами, а не запятыми. Суффикс `.csv` не подтверждает comma-separated формат. Первая строка уже имеет такой же вид; заголовка, имён колонок или комментариев в осмотренных строках нет.
- Первое поле во всех осмотренных строках — буквальный token `W`; token `R` в этих окнах не виден (кандидаты C011/C012 ниже). Это не утверждение об отсутствии чтений во всём файле.
- Второе и третье поля выглядят как положительные десятичные целые; оба изменяются. Тип данных в parser и их физический смысл не проверены.
- Дополнительных колонок с явными именами timestamp, request/device/thread/queue ID, arrival/completion нет в осмотренном формате. Без документации нельзя окончательно исключать иной смысл двух числовых полей.
- Второе поле имеет повторения в hm_0: например, позиции строк 7/9 и 8/10 совпадают соответственно. В prxy_0 заметны участки последовательного роста второго поля при одинаковом третьем: строки 1–4 и 47–76. Это описание чисел, не доказательство последовательных I/O или предсказуемости.

**HYPOTHESIS — не подтверждённая схема:** `operation | starting address/offset | request length/count`. `W` может означать write, поле 2 — адрес, поле 3 — длину. Эти значения правдоподобны по форме, но требуют provenance/schema. Не установлено, являются ли адреса bytes, sectors, LBA или pages; длины могут иметь иную единицу, чем адреса. Размер sector/page и namespace UNKNOWN. Из имён hm/prxy/суффикса 0 не выводятся MSR, workload role, device ID, год, лицензия или версия.

**INFERENCE — возможная проблема единиц, не диагноз:** по ранее сохранённому simulator-audit.md §4 parser ожидает whitespace `operation starting-sector sector-count`. Внешнее совпадение трёх полей не устанавливает совместимость: если поле 2 здесь byte offset, его нельзя непосредственно подавать как sector address. Аудит симулятора также фиксирует modulo address wrapping, способный менять locality. До проверки единиц никакого преобразования или replay не делать; не переносить размер page симулятора на данные автоматически.

**Различие workloads:** два разных локальных файла и различающиеся видимые числовые последовательности подтверждены. Два независимых workload/device/session не подтверждены. Начальные фрагменты могут отражать лишь одну фазу; происхождение, связь файлов, порядок и способ преобразования исходных трасс неизвестны.

## 4. Применимость к следующему read и ограничения вывода

**Что известно:** в осмотренных окнах есть только `W`, нет наблюдаемой последовательности `R`. **Что неизвестно:** есть ли read события дальше, сохранены ли все операции и их хронология, не отфильтрованы ли чтения при подготовке файлов. Из этих образцов нельзя сформировать или оценить next-read target; даже значение W ещё нуждается в документации. Предсказуемость, accuracy, precision, throughput и выигрыш не измерялись.

**Условное предложение, не выбор задачи/модели:** если подтвердятся операция read, логические адреса, единицы и исходный порядок, можно определить прогноз адреса следующего read request по доступной к моменту решения истории. Прогноз следующей page — отдельное определение: запрос может покрывать несколько страниц, и их искусственный порядок развёртки нельзя выдавать за наблюдаемый порядок чтений. Нужны granularity, address namespace, глобальный поток или конкретная queue/device, момент решения, k/горизонт и допустимость истории writes. Пока они не утверждены.

Если полный профиль покажет только writes, это блокер для эмпирической оценки next-read на этих файлах, а не повод незаметно заменить задачу next-write или сгенерировать reads. Потребуется запросить подходящие данные или согласовать версионированное изменение вопроса. Сейчас такой полнофайловый вывод не делается.

### Split/leakage — вопросы для будущего протокола

- Temporal train/validation/test имеет смысл только при подтверждённом хронологическом порядке. Порядок строк может оказаться результатом фильтрации/сортировки; его здесь не валидировали. При отсутствии времени допускается лишь явно оговорённая событийная задача, не оценка своевременности миграции.
- Не перемешивать зависимые запросы случайно. Не делать «по одному файлу на train/test» только из имён: сначала установить независимость/перекрытие происхождения и address namespace. Повтор адреса сам по себе не leakage; повтор одной исходной записи в разных split может быть им.
- Все входные features — только уже доступное прошлое; статистики частот, нормализация, vocabulary и прочая обучаемая подготовка не должны подгоняться по будущему test. Если заранее известная геометрия устройства нужна, её источник указать отдельно.
- Окна и future labels у границ split могут пересекать соседнюю часть. Правило разрезания/исключения граничных примеров и переноса исторического состояния нужно зафиксировать заранее; произвольный gap здесь не выбирался.
- Определить, какие writes допустимы в истории до следующего read, и правила stream/queue ties. Оценивать на фиксированных test границах; модель/параметры выбирать не по test.
- Запросы/окна/два имени файла не устанавливают число независимых реплик. При одной или связанных трассах будущие выводы ограничиваются их временными holdout, без притворной независимости.

Prediction quality — отдельный prerequisite. Primary системная метрика уже делегированно выбрана в decision log: useful completed demand-read MiB/s, secondary IOPS. Они **не вычислялись**. Даже успешный predictor не устранит serial timing limitation C010 и не докажет ускорение SSD.

## 6. Уточнения и рекомендуемый ограниченный следующий шаг

1. Запросить исходный источник/описание колонок и историю preprocessing: смысл W/R, единицы адреса/длины, sector/page size, namespace; были ли удалены timestamps/reads/IDs, сохранён ли порядок. Уточнить право локального использования, лицензию и ограничения приватности; не отправлять трассы в сеть.
2. Получить **отдельное явное разрешение** на read-only локальный Python для полного профиля; текущего согласия на native sample audit недостаточно для выполнения команд. Предлагаемый объём: оба файла, один потоковый проход на файл для bytes/SHA256/row counts/формата/op mix/числовых ranges; порядок времени — только если найдётся подтверждённый timestamp. Без timestamps по одним адресам нельзя проверить хронологию. Для выявления только-write случая опираться на полный op mix, не искать удобные фрагменты выборочно.
3. До этого прохода согласовать конечный лимит времени/RAM и место отдельного нового отчёта; показать и проверить код/зависимости, запускать локально без сети и без записи в dataset/. Вывод — агрегаты и provenance, без raw адресов/идентификаторов/credentials. Фиксировать CPU/RAM/OS/runtime, версию скрипта, команды/exit codes и статус частичного/неуспешного чтения. При исчерпании лимита сохранить partial status, не объявлять полный профиль. Это предложение, скрипт и запуск здесь не создавались.
4. Для будущего training checkpoint отдельно нужны точная дата/число дней, доступные CPU/RAM (GPU не предполагается), finite training/tuning budget, target/splits и независимая единица. Scientific protocol approval и shell permission — разные разрешения. Выбор модели, утверждение протокола и обучение не входят в этот аудит.

**Рекомендация:** сначала provenance/schema и разрешённый ограниченный полный read-only профиль, затем передать проверенные свойства методологу для плана первого predictor. Если профиль или происхождение не доступны, сохранить блокер, не подменять его предположениями.
