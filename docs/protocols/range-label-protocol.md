# Разметка по диапазонам байтов: гранулярность 512 Б и частичные перекрытия

Протокол фиксируется до расчёта новых метрик исходов. Все дни 5–7 уже просмотрены: эксперимент диагностический, независимого holdout нет. Старые результаты, модели и frozen selections не изменяются; вывод — в новый каталог `results/range-label/`.

## Проверенные постановочные факты (до фиксации метрик)

Источник: полные загруженные префиксы до 168h из `results/all-write/<workload>/events.bin` (usr_1 — 45 283 980 событий, prxy_1 — 168 638 964). Поля по SNIA IOTTA README §3 (проверено 2026-09-30, `.research/claims/evidence-map.md` C015): `Timestamp` — время поступления запроса (issue time, Windows FILETIME), `ResponseTime` — длительность завершения I/O в тех же единицах FILETIME (не абсолютное время), `Offset`/`Size` — байты.

1. Выравнивание: во всех событиях обоих префиксов `Offset % 512 == 0` и `Size % 512 == 0` (нарушений 0). Сетка 4 KiB невозможна: у usr_1 45 283 936 из 45 283 980 событий имеют `Offset % 4096 == 3584`; у prxy_1 остатки равномерно смешаны.
2. Размеры запросов: usr_1 — 74,09% = 64 KiB, 18,45% = 4 KiB, максимум 512 KiB; prxy_1 — 57,43% = 8 KiB, 24,01% = 4 KiB, 9,82% = 60 KiB, максимум 1 MiB. Больше 99% событий охватывают несколько 512-байтовых блоков.
3. Кэши `events.bin` не содержат `ResponseTime`; момент прогноза во всех прежних этапах — поступление Write, оба конца интервала — issue time. Основная разметка сохраняет эту конвенцию. Чувствительность к временам завершения (`Timestamp + ResponseTime`) допускается только отдельной ограниченной проверкой на выборке после основных результатов и не меняет основную разметку.

## Определения

- Диапазон события — полуинтервал `[Offset, Offset + Size)`. Все концы лежат на сетке 512 Б, поэтому диапазон — объединение полных 512-байтовых блоков, и байтовое пересечение диапазонов эквивалентно пересечению на сетке 512 Б. Блок B = 512 Б — единственная обоснованная общая сетка: более грубая опровергается п. 1, более тонкой в данных нет. Округление концов к сетке обязано быть no-op и проверяется на каждом запуске.
- Версия Write W — её диапазон байтов, выпущенный в момент `Timestamp` (issue time).
- Read R потребляет версию W, если `R.index > W.index` (порядок строк источника; равные timestamps разрешаются порядком строк — та же конвенция, что на всех прежних этапах) и диапазоны пересекаются.
- Write W′ перезаписывает версию W, если `W′.index > W.index` и диапазоны пересекаются. Любое пересечение консервативно уничтожает всю версию (вариант A). Степень частичности отдельно измеряется и публикуется; поблочное выживание версий (вариант B) в этот этап не входит и фиксируется как последующее решение.
- Исход Write: первое по порядку строк событие после W (Read или Write, пересекающее диапазон) даёт Read-first (1) или Write-first (0); если до границы наблюдения первого события нет — цензурировано (−1). Цензурированные случаи не становятся отрицательными исходами и не получают нулевых ошибок.
- Target при Read-first: `(Timestamp(R) − Timestamp(W)) / 10^7` секунд, issue-to-issue. Budget для критерия `error < budget`: задержка до первой пересекающей Write; если её нет до границы — `граница − Timestamp(W)`.
- Прежняя разметка («точный начальный Offset») переиспользуется как база сравнения и переопределяется в новом модуле: следующий Read/Write с тем же начальным Offset и большим порядком строк, размер игнорируется.

## План сравнения (день 7, те же срезы, что в all-write/window-outcome)

1. Воспроизведение прежней разметки: счётчики исходов дня 7 обязаны совпасть с опубликованными (usr_1: 127 352 / 399 818 / 264 043; prxy_1: 1 954 199 / 6 398 319 / 105 508 при 791 213 и 8 458 026 всех Write).
2. Исходы по диапазонам: доли Read-first / Write-first / цензурирования и изменение против прежней разметки — число и суммарный байтовый объём Write-запросов (повторные записи считаются повторно), у которых совпавший Read или совпавшая Write изменились.
3. Диагностика частичности среди совпавших первых Read: точное совпадение начала и размера; то же начало, другой размер; начало внутри записанного диапазона; покрывающий Read (диапазон Read ⊇ диапазона Write); число Write, частично перезаписанных до первого Read.
4. Критерии на сопоставимых наборах без переобучения: сохранённые per-Write прогнозы `current` из `results/all-write/*/day7.predictions.npz`. Считаются (а) подтверждённая доля `|pred − target| < budget` на прежнем наблюдаемом наборе — обязана воспроизвести опубликованную; (б) та же доля на новом наблюдаемом наборе; (в) на Write, наблюдаемых в обеих разметках, — обе версии доли; (г) нулевой прогноз (`target < budget`) — разметко-зависимая величина без модели. Каждый знаменатель публикуется явно.
5. Никакого переобучения, поиска порогов или нового frozen selection. Результаты диагностические; сравнение методов допустимо только на идентичных наборах, изменение знаменателя публикуется отдельно.

## Реализация и память

Точный расчёт на сетке 512 Б: обратное развёртывание с бегущим per-block минимумом индексов будущих Read и будущих Write; блоки сжимаются до уникальных, затронутых событиями дня 7; пары блоков строятся чанками, события удерживаются только как disk-backed массивы. Медленная эталонная реализация per-Write на случайной выборке обязана совпасть с быстрой точно. Прежняя разметка воспроизводится через сортировку по (Offset, порядок строк). Прогнозы `current` берутся из сохранённых npz, модели не загружаются.

## Ручные тесты до метрик

Частичное перекрытие (Read с началом внутри записанного диапазона), большой покрывающий Read, повторная Write до Read (прежняя разметка даёт Read-first, новая — Write-first), равные timestamps (порядок строк), Read с тем же timestamp, но меньшим порядком строк не потребляет, отсутствие будущих событий даёт цензурирование, no-op проверка сетки 512 Б, отклонение невыровненных входов.
