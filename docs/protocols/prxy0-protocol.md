# Проверка prxy_0: протокол до метрик

Источник: исходный `MSR-Cambridge/prxy_0.csv.gz` из
`dataset/msr-cambridge1.tar`, не преобразованный CSV без timestamp.
Читаем первые 168 часов от первого события до EOF, без ограничения по
числу событий, способного обрезать эту трассу (cap 100 млн; достижение cap — ошибка).
Проверяем хронологию, единый logical volume, сетку 512 Б. Время issue-to-issue;
равные timestamp разрешаются порядком строк.

## Постановки

1. Исходная: первое последующее Read с тем же начальным Offset, независимо
   от промежуточных Write. Перезапись — первый последующий Write с тем же Offset.
2. Диапазонная: первое последующее пересекающее Read и пересекающее Write.
   Любое пересечение считается совпадением, не полным прочтением/заменой версии.

Для каждой постановки публикуем Read-first / Write-first / unresolved,
все Write, число наблюдаемых Read, число наблюдаемых перезаписей.
Write-first не исключаем из исходного критерия прогноза времени чтения адреса.

## Обучение и выбор

День 1: train [0,14.4h), validation [14.4h,19.2h);
последние 4.8h дня 1 не используются для выбора и не объявляются holdout.
Labels не пересекают соответствующую границу. Признаки — семь существующих
past-only same-start признаков; модели диапазонной постановки используют те же признаки.
Для каждой постановки ровно два LightGBM log-L2: все признаки / без read/write counts.
150 trees, 31 leaves, learning rate .05, min_child_samples 50, reg_lambda 1,
seed 42, 2 threads. Baseline: global median и per-address median training labels.
Выбор среди четырёх методов по validation MAE; без дополнительного tuning,
без переобучения на validation. Модель и baseline замораживаются до будущей оценки.

## Будущая оценка

Дни 2–7, каждое окно 24h отдельно; truth обрезается концом окна.
История признаков обновляется причинно, веса и baseline не меняются.
Первый просмотр будущих результатов prxy_0 в этой серии; не независимый workload
от семейства MSR и той же proxy-группы. Все дни публикуются, включая неудачные.

Критерий: строго `abs(predicted_read_delay - actual_read_delay) < overwrite_delay`.
Основной знаменатель — Write с наблюдаемым Read в окне, как в submission.
Если перезапись не наблюдалась, оставшееся время окна задаёт нижнюю границу бюджета;
pass с меньшей ошибкой подтверждён, остальные случаи неизвестны, а не failures.
Публикуем lower/upper pass bounds, N, coverage от всех Write, MAE/P90,
а также confirmed pass / все Write (не называем это основной observed-метрикой).
Отдельно диагностируем Read-first группу без представления oracle-фильтра как gate.
Pooled MAE и bounds считаем по строкам, не как среднее процентов дней.

## Проверки и артефакты

Новый каталог `results/prxy0-check/`; не перезаписывать существующий запуск.
Сохраняем source hash, model files, frozen selection до оценок, labels/predictions,
метрики и протокол/code hashes. Независимая проверка для до 128 Write в каждом
будущем дне: прямой поиск первого Read/Write по обоим правилам.
Сверяем causal features/targets на коротком префиксе с простым forward/reverse
pipeline; сравниваем saved predictions с моделью на выбранных строках.

## Поправка после проверки доступности train/validation, до будущих метрик

Первый запуск остановлен до обучения: same-start train имеет 288 labels,
validation — 0; range train — 476, validation — 2. Нельзя выбирать модель по
такому validation. Для обеих постановок, если validation N < 100, заранее
фиксируем `no_counts` (рецепт prxy_1 submission), без объявления его победителем.
Остальные фиксированные методы публикуем как сравнение, но не используем будущие
дни для смены выбранного метода. Возобновляем загрузку из уже сохранённого
events/features cache, не перезаписывая их. Новая настройка по будущим данным
не разрешается. Это exploratory проверка при крайне слабой обучающей выборке.
