# Второй этап: диапазонная проверка кандидатов до обучения

После первого скрининга все шесть новых рекомендованных трасс (`proj_1`, `prn_1`,
`hm_0`, `prn_0`, `usr_0`, `proj_0`) проверяем на **любое пересечение** диапазонов.
Окна, границы labels и пороги достаточности те же, что в
`data-sufficiency-protocol.md`; будущие дни не просматриваем.
Каталог `results/data-sufficiency-range/`. Сохраняем disk-backed events первого
19.2h, source hashes и labels. Сверяем source prefix с первым этапом, а до
128 Write каждого окна независимо проверяем прямым линейным поиском.
Distinct labelled offsets — начальные адреса запросов Write, distinct target
Reads — уникальные строки первого пересекающего Read. Это проверка объёма и
разнообразия данных, не оценка будущей точности и не гарантия 90%.
