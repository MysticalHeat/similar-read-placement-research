# Скрининг достаточности данных до обучения

Проверяем все исходные `*.csv.gz` в двух локальных MSR-Cambridge tar.
Не используем преобразованные CSV. Каждый logical volume отдельно.
Новые метрики только в `results/data-sufficiency/`; старые результаты сохраняем.

## Окна и label

От первого события каждой трассы: train [0,14.4h), validation [14.4h,19.2h).
Читаем до первого события >=19.2h либо EOF; дни 2–7 не просматриваем.
Строгая хронология, порядок строк при равных timestamp, один volume, положительные
512-byte-aligned размеры/offset. Label — первое последующее Read с **тем же
начальным Offset**, как в submission, независимо от промежуточной Write.
Labels не пересекают границы окон. Отдельно считаем Read-first, Write-first,
unresolved внутри окна. Unresolved не превращаем в отрицательный label.

Этот первый скрининг отвечает на достаточность исходной same-start постановки.
Он не заменяет отдельную проверку диапазонных labels и пригодности gate перед
range-refit; малое число same-start labels не доказывает малое число range labels.

## Заранее фиксированные критерии

Практический минимальный фильтр, не гарантия качества/статистической независимости:

- Полное окно наблюдения до 19.2h (иначе недостаточная длительность).
- Train >=10 000 завершённых labels и >=100 разных labelled Offset.
- Validation >=2 000 завершённых labels и >=50 разных labelled Offset.

Для условного прогноза Read-first/gate дополнительно отмечаем train >=1 000,
validation >=200 Read-first примеров. Это отдельный индикатор, а не условие
допуска исходной задачи. Для классификатора ещё потребуется проверить оба класса.

Публикуем все трассы, включая не прошедшие фильтр: events/Read/Write, observed
labels, coverage, distinct labelled offsets, largest-address label share,
effective address count (1/sum(p_address**2)), validation label share на
адресах с training labels. Большое число повторных Write перед одним Read
не является таким же числом независимых наблюдений: считаем также число Read,
которые завершили хотя бы один label (distinct target events). Для надёжности
отдельно отмечаем >=1 000 таких train Read и >=200 validation Read; этот
индикатор учитывается в рекомендации вместе с базовым фильтром.

Ранжирование новых трасс, прошедших оба фильтра: больше validation distinct target
Read, затем train distinct target Read. usr_1/prxy_1/prxy_0 — контрольные нагрузки,
не новые кандидаты. Никакого выбора по будущим MAE/pass, модели не обучаем.

## Проверки

Прямой потоковый счётчик: pending Write по Offset; первый Read завершает
все ожидающие labels по этому Offset. При границе окна pending сбрасывается.
Независимая сверка на первом префиксе до 2 000 событий каждой трассы через
существующий forward/reverse pipeline, с отдельной обработкой границ.
Unit-проверки: несколько Write до Read, разделение окон, цензурирование,
порядок равных timestamp. Записываем SHA256 просмотренного префикса и code hash.
