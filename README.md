# Прогноз следующего чтения в момент записи

Новый этап улучшения MAE: [reports/mae-improvement.ru.md](reports/mae-improvement.ru.md). Настройки и причинные признаки выбираются на уже известных днях 2–4, затем замороженные кандидаты проверяются на днях 5–7. Артефакты и проверка: [results/mae-improvement/README.md](results/mae-improvement/README.md).

Сопоставление с временем до перезаписи: [reports/overwrite-comparison.ru.md](reports/overwrite-comparison.ru.md). Отдельно сравниваются средние, типичные интервалы и ошибки каждой записи; неизвестные перезаписи учитываются через границы, без новых fits.

Поиск с порогом 90%: [reports/overwrite90.ru.md](reports/overwrite90.ru.md). Выбор направлен на долю ошибок меньше перезаписи; новые модели и обновляемые прогнозы сравниваются на одинаковых записях дня 7. Это повторная диагностика уже просмотренных данных.

Двухэтапный Read-first: [reports/read-first.ru.md](reports/read-first.ru.md). Причинный отбор чтений до повторной записи, условный прогноз времени и отдельный контроль общего критерия и покрытия.

Полная выборка Write и finite-window исходы: [reports/all-write.ru.md](reports/all-write.ru.md). Новые признаки серий I/O, учёт неизвестных исходов и покрытие по всем Write, а не только завершённым Read.

**Минимальный комплект для сдачи: `submission/` — `results.ipynb`, `training.ipynb`, `usr_1.lightgbm.txt`, `prxy_1.lightgbm.txt`. В notebooks код и краткое описание features/labels. Для обучения задайте DATASET с исходными архивами; новые модели сохраняются в trained/.**

Цель: для каждой записи предсказать время **от этой записи до первого последующего чтения того же начального байтового адреса**. Временные метки MSR FILETIME переводятся в секунды через разность целых чисел / 10⁷. Исходный пример сеньора — `notebooks/reference/lgb_src1_2_log.ipynb`.

## Метод первого пилота

- Единица: точное совпадение начального `Offset`, не пересечение диапазонов. Один файл — один logical volume, проверяется при чтении.
- Момент прогноза: поступление `Write`. `ResponseTime` не используется.
- Цель: первый следующий `Read` по порядку строк; одинаковые timestamps допускают нулевой интервал.
- Несколько записей до чтения имеют разные интервалы до одного чтения. Это прогноз обращения к адресу, не конкретной версии данных.
- Признаки: log1p адреса и размера, предыдущих счётчиков чтений/записей, времени с предыдущего чтения/записи, последнего завершённого read→read интервала. Отсутствующая история — NaN.
- Хронологический split 60/20/20 **по длительности наблюдения**, границы — первое событие не раньше соответствующей временной отметки. История holdout обновляется наблюдаемыми событиями, но модель и baseline не переобучаются. Если в split нет завершённых интервалов, его метрики недоступны; фиксированная модель не использует validation для настройки.
- Разметка обучения не использует чтения после начала validation; разметка validation — после начала test. Записи без чтения до конца своего split считаются **right-censored** и не участвуют в регрессии/оценке. Coverage публикуется отдельно. Это ограничивает выводы о длинных интервалах и обо всех записях.
- Baseline: глобальная медиана и медиана для адреса по завершённым обучающим интервалам (fallback к глобальной медиане).
- LightGBM: фиксированные 150 деревьев, 31 leaf, learning rate 0.05, 2 потока; регрессия log1p секунд, без подбора параметров.
- Метрики: MAE, median AE, P90 AE, RMSE в секундах и MAE log1p секунд. Оптимизация логарифмической ошибки не гарантирует лучшую MAE в секундах.

## Артефакты первого пилота

`results/next-read-pilot/`: `results.json` (параметры, версии, SHA256 фактически прочитанного префикса и кода, coverage, метрики, время и RSS), `report.md`, две LightGBM-модели и CSV прогнозов validation/test. Время в CSV относительно первого события своей трассы. `notebooks/history/next_read_prediction.ipynb` отображает сохранённые результаты; ячейка запуска отключена по умолчанию.

Для работы с ноутбуком: `uv sync --extra notebook`, выберите Python `.venv/bin/python` как kernel. Обучение можно запускать CLI без Jupyter.

После обучения `uv run --extra notebook python -m read_prediction.checks.pilot` независимо пересчитывает MAE из CSV, проверяет границы окон, модели и hash кода, затем выполняет ноутбук в памяти без повторного обучения. Интерпретация первого результата: `results/next-read-pilot/interpretation.md`.

Первый эксперимент оценивает предсказуемость на начальных фрагментах двух нагрузок, не всю неделю и не ускорение SSD. Следующие шаги: увеличить временное покрытие, оценить цензурированные интервалы отдельно и согласовать переход от начальных адресов к блокам.

## Продолжение: первые 24 часа обеих нагрузок

Готовый понятный итог: **`results/next-read-24h/summary.md`**. Подробные метрики — `report.md` и `results.json` в том же каталоге, независимая проверка — `verification.json`. В ноутбуке добавлен раздел суточного эксперимента.

```bash
# Новый каталог нужен, чтобы сохранить уже выполненный запуск.
uv run python -m read_prediction.extended --hours 24 --max-events 40000000 --output results/next-read-24h-new
# Проверка сохранённого основного запуска, без нового обучения:
uv run python -m read_prediction.checks.extended
```

Обработано 10,64 млн событий usr_1 и 25,09 млн prxy_1. Новая подготовка использует компактные события на диске, стабильную группировку по Offset и mmap признаков. Семантика истории и разметки совпадает с первым pipeline. Временные кэши удаляются после успешного результата. Полные validation/test прогнозы хранятся в `.predictions.npz`, а не CSV; открыть через `numpy.load`. Суточный протокол — `docs/protocols/next-read-24h-protocol.md`.

**По средней ошибке модель лучше baseline на usr_1 (77,06 против 112,84 минуты), но хуже на prxy_1 (18,11 против 8,36 секунды).** Параметры LightGBM прежние, подбора по test нет. Ошибки вычислены среди записей с чтением внутри split; покрытие test — 11,86% и 53,41%. Старый короткий пилот сохранён отдельно.

### Подготовительный аудит и изменение протокола

До обучения проверены 300 000, затем 1 000 000 событий `usr_1` с разбиением 60/20/20 по числу событий. Первый вариант дал 1 905/0/0 завершённых интервалов train/validation/test; второй — 6 049/1/0. Обе попытки остановились до обучения. Причина: высокая интенсивность запросов в конце префикса сжимает временные окна holdout. Поэтому окончательный протокол использует миллион событий и 60/20/20 по **времени** для обеих нагрузок; это изменение по наличию разметки, не по качеству модели. В `usr_1` validation по-прежнему пустой, test имеет 796 завершённых интервалов. Никакой настройки модели по test нет.

## Диагностика проигрыша prxy_1

Итог и объяснение: **`results/prxy-validation-diagnosis/summary.md`**. На train/validation проверены три фиксированных варианта без повторной оценки test. Удаление накопленных счётчиков из прежней log-L2 модели снизило validation MAE с 17,28 до **3,90 секунды**; медиана адреса даёт 9,16 секунды. Смена функции обучения тоже помогла. Выбранный вариант сохранён в `selected-model.json` и `no_counts_log_l2.lightgbm.txt`; последующие проверки — в `results/prxy-day2/` и `results/final-study/`.

Команда нового диагностического запуска: `uv run python -m read_prediction.experiments.diagnosis` (каталог результатов должен отсутствовать; текущий результат не перезаписывается). Проверка текущих артефактов: `uv run python -m read_prediction.checks.diagnosis`. Протокол до обучения: `docs/protocols/prxy-diagnosis-protocol.md`. В notebook истории добавлен раздел диагностики.

Проверены 4,45 млн завершённых интервалов, coverage 53,92%; редкие крупные ошибки остаются. Новый период не использовался для выбора модели.
